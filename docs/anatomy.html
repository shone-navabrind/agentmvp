System anatomy

Harness Cloud

A workspace holds many projects. Each project owns one small virtual machine. Many agent sessions work inside it at once, on their own branches, without stepping on each other.

Most of this document is two pictures. The first shows what the system is made of and which way the arrows point. The second shows the one mechanism that is easy to get wrong: how a described stack and a curated one end up in the same place.

What it is made of

Three bands. Everything above the dashed line runs on servers you control. Everything below it runs in a machine that belongs to one project and can be thrown away.

Two ways in, one pipeline

A customer either picks a ready-made environment or describes one. The tempting mistake is to build a second code path for the described case. This design refuses that: synthesis emits the same artifact the catalog holds, so an unanticipated stack is exactly as debuggable as a curated one.

Uploaded data is scrubbed before the assistant sees it

A production dump carries real people. An Odoo database restored as-is will email real customers the moment its scheduled jobs wake up. Neutralisation is on by default and runs inside the restore step, not as a thing someone remembers to do afterwards.

  • Contact details replaced, not deleted, so the shape of the data survives.
  • Outgoing mail servers disabled.
  • Scheduled jobs switched off.
  • For WordPress, the site address is repointed at the private preview.

One interface, three amounts of machinery

There is no separate simple app. The same shell, the same API and the same capabilities serve everyone; the role decides how much is on screen and what it is called. Someone who never wants to see a branch name never sees one, and nothing is taken away from them.

Why many sessions share one machine

A VM per session is too expensive and too slow. A shared directory is a corruption bug waiting to happen. The answer is one bare clone per repository and a git worktree per session: three agents can edit the same file at the same time, each on its own branch, and git diff answers what each one changed.

Filesystem

One worktree per session, one branch each. Promotion to main is always explicit.

CPU and memory

A systemd scope per session. A runaway build starves itself, not its neighbours.

Ports

A disjoint block per session, so two dev servers can both want 5173.

Admission control caps concurrency at whichever of memory or CPU binds first and queues beyond it, visibly. The prototype's agents were OOM-killed because nothing refused the extra work.

Not built, and why

Real Incus VMs need KVM, which the build container does not have, so the driver is written in full and only its command construction is tested. sandboxd needs a real VM to live in. The LiteLLM gateway and the pi harness need provider keys and installed CLIs. Authentication and SSO are not started; the capability layer above them is complete and table-driven.

Every number on this page comes from the test suite, not from an estimate. The accessibility gate runs axe-core against the rendered DOM of all nine views at WCAG 2.1 AA and fails the build on any violation.
